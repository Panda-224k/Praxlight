# HANDOFF — PHASE 2

## Status

**COMPLETE**

## What Was Implemented

`extension/content/perception.js` hardened per the Phase 2 spec, additively:

- `disabled` / `required` / `checked` on form fields (`extractInputs`)
- `disabled` (including `aria-disabled`) on interactive controls
  (`extractInteractive`)
- `ariaMetadata(el)`: `ariaLabel`, resolved `ariaDescribedBy` text (follows
  the ID reference to the actual element and reads its text, not just the
  raw attribute), `ariaRequired`, `ariaInvalid`, `ariaExpanded`,
  `ariaPressed`, `ariaChecked`
- `nearestFormId(el)`: uses the native `.form` property so `form="..."`
  attribute-based associations work, not just DOM nesting
- `isInViewport(bbox, win)`: deliberately separate from the pre-existing
  `isVisible` (CSS-visibility) check
- top-level `capturePage()` additions: `schemaVersion: "0.2.0"`, `viewport`
  (width/height/scrollX/scrollY), `shadowHostCount`
- `extractIframes(doc)`: same-origin iframes perceived one level deep
  (inputs/interactive/text), cross-origin iframes reported as
  `sameOrigin:false` with an explanatory note rather than silently omitted
- `collectAllRoots(root)`: traverses into *open* shadow roots for input,
  interactive, and text extraction. Closed shadow roots are not and cannot
  be handled — that's `Element.attachShadow({mode:"closed"})` making the
  tree genuinely unreachable from any script by browser design, not a gap
  in this implementation. Documented as such rather than glossed over.
- Bugfix: `isVisible` now calls `getComputedStyle` via the element's own
  `ownerDocument.defaultView` instead of always the top-level window —
  necessary for the new same-origin iframe perception to report visibility
  correctly, and correct regardless of iframes.

Every field present before Phase 2 kept its exact name, type, and meaning.
No consumer of `perception.js`'s output (`content-script.js`, `detectors.js`,
`redaction.js`) was modified.

`tests/test_perception.cjs` created: 13 tests using jsdom, covering every
addition above plus the pre-existing `isVisible`/`extractText` behavior.
`jsdom@30.0.1` added as a dev-only dependency via a new root `package.json`
(the extension and backend remain dependency-free to actually run).

## What Was Not Implemented

  `inViewport`) through `redaction.js`'s `sanitizePerception` so the
  server/agent can see them — out of scope for a perception-only phase,
  flagged as a natural Phase 7/11 follow-up.
- Anything from Phases 3–20 (OCR, vision, fusion, etc.) — not touched.
- Real-browser verification of any of this — jsdom is not Chrome. This
  remains an open item across both Phase 1 and Phase 2.

## Known Bugs

**One found and fixed, in the test suite, not the shipped code**: the first
draft of the same-origin-iframe test failed because jsdom gives an
`<iframe>`'s `contentWindow` its own separate global realm (correctly
mirroring real browser behavior), so the outer test's
`getBoundingClientRect` patch didn't apply inside it, making every element
in the iframe report zero size and therefore "not visible." Fixed by
patching that realm's `Element.prototype` too. No bug found in
`perception.js` itself this phase.

## Important Technical Decisions

- Chose to make every Phase 2 addition purely additive to the existing
  schema rather than restructuring toward the exact example shape shown in
  the phase spec (`{psId, type, role, text, visible, interactive, disabled,
  bbox}`) — that example uses field names (`type` for role-like
  categorization, a single flat shape for both inputs and interactive
  elements) that don't match this codebase's existing, tested,
  already-integrated shape. Renaming risked breaking `detectors.js`,
  `redaction.js`, and 11 passing tests for a cosmetic schema-shape match
  with no functional benefit. The phase's own instruction — "improve the
  existing perception layer instead of replacing it" — supports this
  reading.
- Used jsdom + manual `getBoundingClientRect` patching rather than skipping
  perception tests entirely or than trying to stand up a real headless
  browser in this sandbox (no browser binary available, and downloading one
  is outside this sandbox's allowed network domains). This is a real,
  common, and honest way to unit-test DOM logic without a browser — it is
  explicitly not a substitute for real-browser verification, which is
  called out as still-open in every relevant doc.

  real-browser verification is needed, it has to happen outside this
  sandbox, by the human running the demo.
